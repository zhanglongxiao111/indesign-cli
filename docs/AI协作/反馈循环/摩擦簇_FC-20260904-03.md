## 簇 ID

FC-20260904-03　目标 INDD 已在 InDesign 中打开导致 `INDESIGN_EXPORT_FAILED`，构建完才失败且文案是原始 JSON

## 证据

- 指标：`INDESIGN_EXPORT_FAILED` × `html.build_indesign` 08-19 起 2 次 / 2 session / 2 台工位（08-25 `DESKTOP-HI43JGC` 39 秒后失败，09-01 `LONGXIAO` 94 秒后失败）；全历史 7 次 / 4 session。两次都在下一次原样重跑时成功。
- 脱敏轨迹（作者工位 `.indesign-cli/session.json` 里保留了完整 hostResult）：
  - 真实原因：`errors[0] = {code: "INDD_SAVE_FAILED", message: "无法存储到文件“<name>.indd”，因为该文件已打开。"}`。典型场景是人（或上一轮）在 InDesign 里打开了上一版成品 INDD 看效果，Agent 接着重建同名文件。
  - Agent 看到的 message：`INDD 已保存于 …indd；PDF 已保存于 …pdf；IDML 已保存于 …idml。{"ok":false,"outputs":{…},"counts":{…},"errors":[{"code":"INDD_SAVE_FAILED",…}],"audit":{…几千字符…}}`。遥测里 500 字截断后连 `INDD_SAVE_FAILED` 都看不到。
  - 两处文案问题：① `build-indesign.js` `hostFailureResponse()` 拿到的 `detail.message` 是整个 hostResult 的 JSON 字符串，说明 `lint-feedback.js:125` `underlyingHostFailure()` 没能从这个形状里取出 `errors[0]`；② `landedDeliverables()` 只检查文件是否存在，把**上一版**残留的 INDD 报成"INDD 已保存于"，与 `INDD_SAVE_FAILED` 自相矛盾。
- 影响版本：indesign-cli 0.5.11 / html-indesign 0.2.10。

## 建议通道

- 正常修复（html-indesign）：
  1. 构建前预检：`<outDir>/<outputBaseName>.indd` 若已被 InDesign 打开（按 `fullName` 匹配 `app.documents`），立即以 `OUTPUT_TARGET_OPEN` 失败并给 hint（关闭该文档后重跑；若文档带本工具的 marker label 可由工具自行关闭）。预检成本 1 秒，省掉 40-170 秒的无效构建。
  2. `underlyingHostFailure()` 兼容 hostResult 为 JSON 字符串 / 嵌套在 `data` 里的形状，message 固定为 `<errors[0].code>: <errors[0].message>`，原始 hostResult 只放 `details.hostResult`。
  3. 当 `causeCode` 是 `INDD_SAVE_FAILED` 时不要输出"INDD 已保存于"前缀；`partialArtifacts` 只列本轮真正写出的文件（用 mtime 或 marker 判断）。
- 文档（快通道）：`failure-handling.md` 补一句"目标 INDD 正在 InDesign 里打开会导致保存失败，先关闭再重建"。

## 承接测试

- 错误信息类：单元测试给 `hostFailureResponse` 喂三种 hostResult 形状（对象 / JSON 字符串 / `data` 嵌套），断言 message 以 `INDD_SAVE_FAILED:` 开头且不含 `{"ok":false`。
- 工具缺口类：真机 E2E 先打开目标 INDD 再构建，期望 `OUTPUT_TARGET_OPEN` 在 5 秒内返回。
- 复核指标：下期 `INDESIGN_EXPORT_FAILED` 归零或全部带可读 cause。
